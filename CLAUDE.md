# SysDE — front Angular

Contexte repris d'une longue session de travail. À lire avant toute modification.

## Le projet

SysDE : plateforme web de gestion de l'encadrement technique de l'hévéa (Côte d'Ivoire).

- Front : ce dépôt (Angular 22, `D:\projet_sysde\sysde-front`).
- Back : Spring Boot, dossier voisin `D:\projet_sysde\sysde-back`.
- Un mobile fonctionnant hors ligne se connectera à la même plateforme (non commencé).
- Langue de l'interface et des échanges : français.

## Stack et commandes

Angular 22.2, sans zone (zoneless), composants autonomes, signaux, `OnPush`, nouveau flux de contrôle (`@if`, `@for`).
TypeScript 6.0, ESLint 10, Vitest, Prettier, pnpm 10. Node 22.22.3+ ou 24.15+ obligatoire (voir `.nvmrc`).

```
pnpm install
pnpm start        # http://localhost:4200
pnpm verify       # format, lint, tests, build de production
```

pnpm refuse les imports de paquets non déclarés : ajouter toute dépendance utilisée dans `package.json`.
Les scripts d'installation autorisés sont listés dans `package.json` (`pnpm.onlyBuiltDependencies`).

## Structure

```
src/app/core/      services transverses (config, HTTP, thème, toasts, titres)
src/app/shared/    design system (ui/), modèles, utilitaires sans logique métier
src/app/layout/    coque, barre latérale, configuration du menu (nav.config.ts)
src/app/features/  un dossier par domaine, chargé à la demande
src/styles/        jetons de design, mixins, base
```

Alias : `@core`, `@shared`, `@layout`, `@features`, `@env`.
Un nouveau module = un dossier dans `features/`, une route dans `app.routes.ts`, une entrée dans `layout/nav.config.ts`.

## Design (obligatoire)

- Vert et blanc, police Montserrat (auto-hébergée via `@fontsource`), rendu sobre, sans codes visuels « IA ».
- Toutes les couleurs, rayons et ombres passent par les variables CSS de `src/styles/_tokens.scss`. Jamais de valeur en dur.
- Le violet est réservé aux données (séries de graphiques), jamais à la décoration.
- Clair et sombre : attribut `data-theme` sur `<html>`.
- Messages (toasts, `ui-toast-host`) : fond vert pour un succès (validation, approbation), rouge pour une erreur ou un rejet critique, jaune pour un avertissement, neutre pour une information.
- Accessibilité : focus visible, contraste AA, graphiques doublés d'un tableau pour lecteurs d'écran.
- Réutiliser les composants de `shared/ui/` avant d'en créer. Graphiques en SVG maison, sans bibliothèque.
- Le skill `ui-vert-expert` (compte Claude de l'utilisateur) détaille ces règles.

## État actuel

Menu : Dashboard, Tâches, Planning, Plantations, Reporting, Carte, Paramètres, Compte.

- Planning (`features/planning/`) : menu placé après Tâches, réservé aux postes CS, CF, CO, FS, MO, ES et SE (`core/auth/access.ts`, `planningGuard`, `NavItem.planningOnly`) ; ni les administrateurs ni CD, SU ne le voient. La secrétaire (SE) n'a qu'un onglet **Équipe** (`tabs/equipe.tab.*`) : liste des collaborateurs du secteur, chef secteur compris (`GET /plannings/equipe`), avec filtres par statut (`rosterStatusOf` : Pas de planning / Brouillon / Soumis / Validé / Rejeté) et par poste, recherche, avancement (activités saisies / activités du poste), « dernière saisie » (`AnnualPlan.editedBy` SELF ou SECRETARY, `editedAt`) et une action par ligne (Saisir, Compléter, Corriger, ou Consulter quand le planning est soumis ou validé). Elle **saisit les plannings à leur place** : la route `planning/equipe/:userId` (`tabs/saisie.page.ts`) réutilise `ElaborerTab` avec `PlanningStore.target` (le collaborateur ciblé ; `proxy`, `ownerPoste`, `ownerIsSectorHead`), bandeau « Vous saisissez pour… », fiche, « Enregistrer et passer au suivant » (personnes sans saisie) ; l'API prend un `userId` facultatif (`mine`, `saveLines`, `submit` ; HTTP : `/plannings/collaborateurs/{id}`, `/lignes`, `/soumission`) et n'autorise que la secrétaire du même secteur ; « Soumettre au chef secteur » (ou « Valider le planning » pour le chef secteur, validé d'office) notifie le collaborateur ; la soumission par activité reste réservée au titulaire. **Import d'équipe** (« Importer plusieurs plannings », `TeamImportDialog`, `parseTeamRows` / `TeamMember` dans `planning.rules.ts`, `downloadTeamTemplate` dans `planning.excel.ts`, `ReviewStore.importMany`) : un seul fichier Excel avec une colonne **Matricule** ; contrôle par personne avec les activités de son poste (numéros de ligne du fichier), matricules inconnus, plannings soumis ou validés ignorés, choix ajouter / remplacer / ne pas toucher pour un brouillon existant ; les plannings importés restent en brouillon. Pas d'import par ligne de la liste (il se fait dans l'écran de saisie). Pour les autres, deux onglets : Élaboration (tous ces postes : saisie ligne par ligne ou import d'un fichier Excel `.xlsx` avec modèle téléchargeable, bibliothèques `read-excel-file` et `write-excel-file` chargées à la demande ; enregistrement du brouillon puis soumission) et Validation (chef secteur seulement, **poste de validation** `ui/review-desk.component.*` : deux voies « À examiner » (anomalie de fréquence) et « Prêts à valider » (validation en lot via `BulkApproveDialog`), filtres par poste et recherche, aperçu de l'élément avec cartes d'activité à 12 mois, « Valider et suivant » / « Rejeter… » avec motif, « Détail complet » ouvre les drawers existants ; pastille du nombre d'éléments en attente sur l'onglet (`TabLink.badge`, `ReviewStore.pendingTotal`) et sur l'entrée **Planning** du menu latéral (pour la secrétaire, pastilles « à traiter » sur le menu et sur l'onglet Équipe : nombre de plannings à saisir, compléter ou corriger, `countToDo`, `ReviewStore.todoTotal` ; `PendingReviewService` de `state/pending-review.service.ts`, service racine chargé à la connexion du chef secteur et tenu à jour par `ReviewStore` ; pour cela `PlanningApi` et ses implémentations sont fournis à la racine, plus dans la route) ; contrôle automatique `ReviewStore.assessments` = `checkFrequency` sur les activités actives du poste ; pas de date de soumission, de commentaire de validation, d'annulation ni de notification ; la secrétaire garde les anciens tableaux ; chaque validation ou rejet envoie une **notification** au collaborateur (`core/notifications/notification.service.ts`, démo : gardée dans `localStorage` et adressée par e-mail ; cloche `layout/notification-bell` dans la barre d'outils avec pastille, liste déroulante et toast « Vous avez N nouvelles notifications » à la connexion ; « Confirmer le rejet » utilise la variante de bouton `danger`) ; valide ou rejette avec motif obligatoire les plannings de ses collaborateurs ; un rejet remet le planning en brouillon). Le planning du chef secteur est validé d'office : son Élaboration n'affiche ni le statut (« Brouillon ») ni le bouton « Valider mon planning ». Chaque planning s'affiche en liste ou en calendrier annuel (bascule Liste/Calendrier ; composant `ui/plan-calendar.component.ts`, 12 mois, couleur par catégorie, clic sur un jour = détail, jour vide = ajout ; lecture seule dans la fenêtre de validation). Pour tous les postes (CS, CF, CO, FS, MO, ES), l'onglet Élaboration s'ouvre sur la vue **Activités** (bascule Activités / Calendrier ; la vue Calendrier montre toutes les dates de toutes les activités du planning, avec une carte de détail du jour fixée en bas (`pinDetail`) ; la vue Liste a été retirée de l'Élaboration, la fenêtre de validation garde Liste/Calendrier ; les boutons « Modèle Excel » et « Importer un fichier » sont toujours affichés dans les deux vues (l'import est grisé quand le planning n'est plus modifiable) ; pas de bouton Ajouter, ni dans la vue Activités ni dans la vue Calendrier : les dates s'ajoutent par « Ajouter ce jour » dans la carte du calendrier ou depuis Détails) : un tableau Année, Activité, Fréquence (« 3 par an et par plantation », « 1 par mois et par saigneur », « Non définie » sans fréquence), Statut (À vérifier / Actif / Inactif) et Action, avec un menu **Options** (`ui-options-menu`) contenant **Détails** (drawer `activity-details.dialog.ts` : calendrier annuel (`PlanCalendar`, sans vue Liste) de toutes les dates de l'activité avec les anomalies du dernier contrôle, ajout par la vue Calendrier (« Ajouter ce jour ») et **Modifier** via `PlanLineDialog` avec activité figée ; lecture seule si le planning n'est plus modifiable) et **Vérifier** (contrôle des dates, règles dans `checkFrequency` de `planning.rules.ts` : nombre de séances attendu pour chaque période de la fréquence (an, semestre ou mois) et, quand elle est « par plantation / saigneur / moniteur / groupe », pour chaque lot ou section distinct du planning (colonne « Lot / section » ; une unité absente du planning n'est pas détectable), durée de chaque séance = durée de l'activité, pas de chevauchement ; message d'information si cohérent → Actif, alerte (toast `warning`) sinon → Inactif) ; le bouton **Vérifier mon planning** (dans la barre d'outils de l'Élaboration, visible dans les vues Activités et Calendrier, à côté de Modèle Excel et Importer) ouvre `tabs/plan-check.dialog.ts` : contrôle chaque activité du poste l'une après l'autre (barre de progression, liste d'étapes Préparation / une par activité / Synthèse, première anomalie affichée sous l'étape, bilan final). **Soumission par activité** (CF, CO, FS, MO, ES ; pas le chef secteur, dont le planning est validé d'office) : le menu Options propose **Soumettre**, qui exige des dates cohérentes avec la fréquence, enregistre le brouillon puis soumet cette seule activité au chef secteur (`AnnualPlan.submissions[]`, états `SOUMIS`/`VALIDE`/`REJETE`, absent = brouillon) ; une activité soumise ou validée est verrouillée (`isActivityLocked`, garde dans `PlanningStore` et dans `DemoPlanningApi.saveLines`), un rejet la rend de nouveau modifiable avec son motif (visible dans Détails) ; le statut du tableau affiche Soumis/Validé/Rejeté avant l'état de vérification. La soumission du planning entier reste possible (elle absorbe les activités soumises non validées). Le chef secteur voit dans Validation une seconde carte **Activités soumises** (une ligne par collaborateur et activité, `ReviewStore.activityRows`) et examine chaque activité (`activity-review.dialog.ts` : calendrier, cohérence, Valider / Rejeter avec motif). API : `POST /plannings/mon-planning/activites/{activiteId}/soumission?annee=`, `POST /plannings/{id}/activites/{activiteId}/validation`, `POST /plannings/{id}/activites/{activiteId}/rejet` `{motif}`. Le résultat est gardé dans `PlanningStore` (pas d'API) et repasse à « À vérifier » dès que les dates de l'activité changent. Une ligne = période (date de début et de fin, bornes incluses, une seule ligne même pour une formation de 20 jours), activité, lot/section, heures par jour (champ retiré du formulaire : une nouvelle date reçoit 4 h par défaut, `DEFAULT_HOURS` dans `line.dialog.ts` ; une date modifiée garde les siennes ; la colonne reste dans l'import Excel) et, pour une activité de catégorie Visite, la **plantation** visitée (`PlanLine.plantation`, champ obligatoire du formulaire, texte libre ; absent de l'import Excel ; la carte de détail du calendrier affiche la plantation à la place du lot et des heures pour les visites, « Session n » pour les formations et « Animation n » pour les rencontres (rang de la séance parmi celles de la même activité, par date) ; la règle « par plantation » de `checkFrequency` s'appuie toujours sur le lot/section) ; la fin est proposée d'après la durée de l'activité (jours calendaires) et l'Excel accepte une colonne « Date fin » facultative ; un bloc « Objectifs annuels » (vue Calendrier de l'Élaboration : `PlanObjectives` alimenté par `annualOverview` de `planning.rules.ts`, `PlanningStore.overview`) liste toutes les activités à fréquence avec la barre et le compteur « prévues / objectif » ; pour une fréquence « par plantation… », l'objectif est celui d'une unité × le nombre de lots/sections déjà présents dans le planning pour cette activité (au moins un) ; le dashboard de terrain garde `objectives` (totaux annuels fixes seulement) ; l'activité d'une ligne vient du référentiel Paramètres > Activités, limité aux activités actives du poste de l'utilisateur (un poste sans activité configurée ne peut pas élaborer de planning). API (`PlanningApi`, démo ou HTTP) : `GET /plannings/mon-planning?annee=`, `PUT /plannings/mon-planning/lignes?annee=`, `POST /plannings/mon-planning/soumission?annee=`, `GET /plannings/a-valider?annee=`, `POST /plannings/{id}/validation`, `POST /plannings/{id}/rejet` `{motif}`. Compte de démonstration : `collaborateur@sysde.ci`.

Règles métier dans `data/settings.rules.ts` (testées). API : `SettingsApi` (démo ou HTTP : `/operateurs`, `/contrats`, `/attributions`, `/exercices`, `/utilisateurs`, `/secteurs`, `/activites`, `/permissions` en GET/PUT). Onglet Activités (avant Permissions) : l'administrateur configure, pour chaque poste du planning (CS, CF, CO, FS, MO, ES) et chaque catégorie (Formation, Visite, Rencontre), les activités qu'il peut inscrire à son planning, avec pour chacune une fréquence (`Activity.frequency` : nombre de séances, période an/semestre/mois, « pour chaque » plantation/saigneur/moniteur/groupe ; facultative) et une durée en jours ; une activité se désactive (jamais supprimée) ; libellé unique par poste ; référentiel initial dans `DEMO_ACTIVITIES`. Composants communs : `ui-data-table`, `ui-field`, `ui-dialog-shell`.

## Règles métier utiles (cahier des charges)

- Opérateurs : SAPH, SOGB, TRCI, EXAT, CCP, IDH, CHC.

## Points d'attention

- `.github/workflows/ci.yml` doit être créé à la main (l'outil précédent ne pouvait pas écrire ce fichier). Il lance format, lint, tests et build avec pnpm.
- Dépôt GitHub : `fangba/sysde-front`, branche `main`.
- Avant de livrer une modification : `pnpm verify` doit passer sans avertissement.

- Connexion : page `/connexion` (hors shell), `AuthService` + `authGuard`/`guestGuard` + intercepteur Bearer ; mode démo = e-mail valide + mot de passe ≥ 4 car. ; back réel : `POST /auth/login` → `{token,user}`.
- Tâches : onglets Utilisateur (personnel de l'organisme connecté uniquement), Chef département, Chef secteur (secteur obligatoire, parmi ceux attribués à l'opérateur), Collaborateur (postes CF/CO/FS/MO/ES/SE, secteur facultatif ; colonnes et champs Matricule (format ACRONYME-NUMÉRO, unique), Lot (parmi les lots du secteur attribués à l'opérateur) et Section (texte libre, ex. « A, B »), propres à cet onglet : `User.matricule/lot/section`, `StaffConfig.assignment`) ; `User.sectorId` ajouté.

## Endpoints du back (règle de travail)
Tout endpoint que le front appelle ou prévoit d'appeler (nouvelle route, nouveau paramètre ou corps, règle d'accès, notification à créer côté serveur) est consigné dans le document du projet Claude « SYSDE » : `claude/endpoints-back.md`. À chaque modification d'une classe `Http…Api` ou d'une règle qui concerne le back, mettre ce document à jour (section concernée, état, points ouverts, ligne du journal) dans la même livraison.
